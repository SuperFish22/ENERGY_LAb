## 1. Введение

### 1.1. Область применения

Документ предназначен для двух ролей:

* **администратор Системы** — руководитель Energy Lab с ролью «Руководитель». Он управляет экипажем, критериями, площадками и модерацией. Работает в браузере, разделы 4–5;
* **администратор сервера** — человек с доступом к серверу в РФ и серверу n8n. Он устанавливает, обновляет и восстанавливает Систему, разделы 3, 6, 7.

### 1.2. Краткое описание

Система состоит из следующих компонентов:

| Компонент | Где | Что делает |
|---|---|---|
| `web` — приложение FastAPI (Python 3.12) | сервер в РФ, Docker | сайт, кабинет, API бота |
| `db` — PostgreSQL 16 | сервер в РФ, Docker, том `pgdata` | все данные, включая персональные |
| `nginx` | сервер в РФ, Docker | HTTPS, ограничение `/api/bot/` по IP |
| n8n + Telegram-бот | внешний сервер | команды бота, доставка уведомлений, выгрузка в Google |
| Timepad | внешний сервис | продажа билетов, чеки, возвраты |
| GitHub Actions + GHCR | внешний сервис | проверка кода, сборка образа, развёртывание |

Персональные данные (ФИО, e-mail, телефоны участников; e-mail покупателей; анкеты) хранятся только в `db` на сервере в РФ. Это требование 152-ФЗ, ст. 18 ч. 5. На n8n уходят только ID чатов и тексты уведомлений.

### 1.3. Уровень подготовки

* Администратору Системы достаточно навыков пользователя (см. ЭЛ.И3).
* Администратору сервера нужны Linux (bash, ssh), Docker Compose, основы PostgreSQL и работа с GitHub.

### 1.4. Перечень документации

ЭЛ.И3 «Руководство пользователя», ЭЛ.ИА (настоящий документ), `docs/chtz/` — ЧТЗ модулей, `n8n/README.md` — настройка сценариев n8n, `README.md` — краткая инструкция для разработчика.

## 2. Назначение и условия применения

### 2.1. Требования к серверу в РФ

* 2 vCPU, 2 ГБ ОЗУ, 20 ГБ SSD (на 5 лет работы с запасом);
* Ubuntu 22.04/24.04, Docker 24+ с плагином Compose;
* домен (например, `lab.energy…`) с A-записью на сервер, открытые порты 80 и 443;
* отдельный пользователь `deploy` в группе `docker`.

### 2.2. Требования к серверу n8n

* n8n 1.x;
* исходящий доступ к `api.telegram.org`, `api.vk.com`, Google API и серверу Energy Lab;
* постоянный внешний IP: он прописывается в `nginx.conf`.

## 3. Подготовка к работе: установка и первый запуск

### 3.1. Состав дистрибутива

Репозиторий GitHub `energy-lab`: исходный код (`app/`), миграции (`migrations/`), `Dockerfile`, `docker-compose.prod.yml`, `deploy/` (nginx, резервное копирование), `n8n/workflows/`, `docs/`. Готовый образ приложения публикуется в `ghcr.io/<владелец>/energy-lab`.

### 3.2. Установка на сервер в РФ

```bash
# 1. пользователь для развёртывания
sudo adduser --disabled-password deploy && sudo usermod -aG docker deploy
sudo mkdir -p /opt/energy-lab && sudo chown deploy: /opt/energy-lab

# 2. код и настройки (под пользователем deploy)
git clone https://github.com/<владелец>/energy-lab.git /opt/energy-lab
cd /opt/energy-lab
cp .env.example .env && chmod 600 .env
nano .env                         # заполнить по приложению А

# 3. HTTPS-сертификат (один раз; потом certbot продлевает сам)
sudo apt install certbot && sudo certbot certonly --standalone -d lab.example.ru

# 4. nginx: домен и IP сервера n8n
sed -i 's/lab.example.ru/<ваш домен>/g; s/N8N_SERVER_IP/<IP n8n>/' deploy/nginx.conf

# 5. запуск
echo <GHCR_READ_TOKEN> | docker login ghcr.io -u <логин GitHub> --password-stdin
docker compose -f docker-compose.prod.yml up -d
```

При старте контейнер `web` сам выполняет `alembic upgrade head` (схема БД) и `python -m app.seed` (справочники: роли, 5 отделов, 15 критериев, классификатор форматов, первый руководитель из `ADMIN_EMAIL`).

### 3.3. Проверка работоспособности

```bash
curl -s https://<домен>/health            # → {"status":"ok"}
docker compose -f docker-compose.prod.yml ps   # web, db, nginx — Up (healthy)
```

Затем войдите под `ADMIN_EMAIL` / `ADMIN_PASSWORD` и **сразу смените пароль**: создайте себе приглашение с ролью «Руководитель», зарегистрируйтесь, а учётную запись по умолчанию заблокируйте.

### 3.4. Демонстрационные данные

Для стенда защиты и обучения выполните `docker compose -f docker-compose.prod.yml exec web python -m app.seed --demo`. Появятся 4 прошедших мероприятия с **условными цифрами**, проекты «Ночь в музее» и «Новогодний квиз» и пользователи `*@energy.local` с паролем `demo12345`. На рабочем сервере демо-данные не загружайте.

### 3.5. Настройка n8n и бота

См. `n8n/README.md`. Порядок:

1. Создать бота у @BotFather.
2. Импортировать сценарии.
3. Создать credential с `BOT_API_TOKEN`.
4. Активировать сценарии.
5. Проверить `/start`.

### 3.6. Резервное копирование

```bash
gpg --import lab-backup-public.asc        # открытый ключ руководителей (закрытый на сервере не хранится)
crontab -e
0 3 * * * /opt/energy-lab/deploy/backup.sh >> /opt/energy-lab/backups/backup.log 2>&1
```

Копия на Google Диск включается, если настроен `rclone` с удалённым хранилищем `gdrive` (`rclone config`).

## 4. Описание операций администрирования

Все операции выполняются в кабинете под ролью «Руководитель». Значимые действия пишутся в журнал аудита.

### 4.1. Пригласить участника

1. Меню → **«Экипаж»** → блок «Пригласить».
2. Укажите e-mail, роли («Участник Lab», «Эксперт», «Руководитель») и отдел для эксперта.
3. Нажмите **«Создать ссылку-приглашение»**.
4. Скопируйте ссылку и отправьте человеку лично. Ссылка действует 7 дней.

Сброс пароля: создайте новое приглашение на тот же e-mail. При регистрации пароль заменится.

### 4.2. Изменить роли, отдел, компетентность, заблокировать

1. «Экипаж» → строка пользователя.
2. Отметьте роли, выберите отдел и компетентность (0,5–1,0).
3. Снимите «Активен», чтобы заблокировать.
4. Нажмите «Сохранить».

Ограничения:

* Ручная правка компетентности попадает в историю с причиной. Обычно её менять не нужно: после каждого «Разбора полёта» она пересчитывается сама.
* Роль снять с последнего руководителя нельзя. Держите в Системе минимум двух руководителей (сейчас трое: Александр, Олег, Катя).

### 4.3. Настроить критерии и веса

«Критерии и площадки» → изменить веса отделов α и веса критериев внутри отдела, при необходимости названия → **«Сохранить и нормировать»**. Система сама приводит суммы весов к 1. Новые веса действуют со следующего расчёта прогноза; уже сохранённые прогнозы не меняются.

### 4.4. Площадки

«Критерии и площадки» → «Площадки» → название, адрес, вместимость → **«Добавить площадку»**.

### 4.5. Модерация доски и SOS

Меню → **«Доска и SOS»**. Сверху — SOS-сообщения и вопросы, ждущие решения. Для каждого вопроса:

* «Опубликовать»;
* «Ответить» (ответ виден на доске);
* «Отклонить».

Если вопрос пришёл из бота, автор получит результат в мессенджер. SOS на доску не попадают. Их получают все руководители, у которых привязан мессенджер, поэтому привяжите бота и укажите телефон в профиле.

### 4.6. Реестр и выгрузка

Меню → «Реестр (CSV)» — все мероприятия одной таблицей (открывается в Excel). Карточка проекта → «Выгрузка» — метки для шаблона Google Docs. Автоматическое дублирование в Google Таблицу выполняет сценарий n8n `google-sheets-registry.json`.

## 5. Формирование и ведение базы данных

### 5.1. Состав БД

28 таблиц (миграция `0001_initial_schema`). Основные группы:

| Группа | Таблицы |
|---|---|
| Пользователи | `users`, `roles`, `user_roles`, `experts`, `competence_history`, `link_codes`, `audit_log` |
| Справочники | `departments`, `criteria`, `event_formats`, `venues` |
| Мероприятия | `events`, `stations`, `decisions`, `event_results`, `tickets` |
| Экспертиза | `event_experts`, `expertise_rounds`, `evaluations`, `risk_assessments`, `forecasts` |
| Гости | `feedback`, `feedback_stations`, `questions` |
| Работа команды | `tasks`, `discussions`, `messages`, `notifications` |

### 5.2. Ввод исторических данных (база аналогов)

Прогноз (метод Г) строится по мероприятиям в статусе «Проанализирован». Чтобы внести прошлые мероприятия ENERGY:

1. Создайте проект с реальными названием, форматом, датой, ценой, вместимостью, бюджетом и станциями.
2. Как руководитель проведите его по статусам до «Проведён».
3. Или быстрее: «Проекты» → «Внести прошедшую тусовку» (одна форма с фактом и фото), затем во вкладке «Итоговая оценка» поставьте оценку гостей и нажмите «Завершить разбор полёта».

Минимум для работы прогноза — 3 таких мероприятия, рекомендуется 8–10. Сейчас в демо-базе 4 мероприятия с условными цифрами. Их нужно заменить реальными: «Велесовы тропы», «Не та сказка», «Алое восстание», «Секреты Ренессанса».

### 5.3. Изменение структуры БД

Структура меняется только миграциями:

```bash
# у разработчика, после правки app/models.py
alembic revision --autogenerate -m "что изменилось"
# проверить файл в migrations/versions/, закоммитить — CI проверит миграции на PostgreSQL 16
```

На сервере миграции применяются автоматически при старте контейнера.

### 5.4. Резервные копии и восстановление

* Ежедневно в 03:00 скрипт `deploy/backup.sh` делает `pg_dump` → gzip → шифрование GPG. Хранятся последние 14 копий в `backups/` и, если настроен rclone, на Google Диске.
* Тот же скрипт обезличивает покупателей мероприятий старше 30 дней и чистит очередь уведомлений (`python -m app.maintenance`).
* Восстановление:

  ```bash
  gpg --import private.asc     # закрытый ключ руководителя — только на время восстановления
  docker compose -f docker-compose.prod.yml stop web
  docker compose -f docker-compose.prod.yml exec db dropdb -U energy_lab energy_lab
  docker compose -f docker-compose.prod.yml exec db createdb -U energy_lab energy_lab
  ./deploy/restore.sh backups/energy_lab_2026-11-20_0300.sql.gz.gpg
  docker compose -f docker-compose.prod.yml start web
  gpg --delete-secret-keys <ключ>
  ```

* Раз в квартал проверяйте восстановление на отдельной тестовой БД.

### 5.5. Защита данных

* Пароли хранятся как хеши scrypt.
* Файл `.env` имеет права `600` и не попадает в git.
* Доступ к БД снаружи закрыт: порт 5432 не публикуется.
* Журнал аудита хранится в таблице `audit_log`.
* По запросу человека на удаление его данных заблокируйте учётную запись и обезличьте ФИО и e-mail (SQL-скрипт в разделе 7). Проекты и оценки останутся для статистики.

## 6. Обновление: CI/CD

Разработчик не имеет доступа к серверу. Обновление идёт так:

1. Разработчик отправляет изменения в GitHub. Workflow **CI** проверяет:
   * линтер;
   * тесты;
   * покрытие расчётных модулей ≥ 90 %;
   * миграции на PostgreSQL 16;
   * сборку образа.
2. После слияния в `main` workflow **Deploy** собирает образ `ghcr.io/…/energy-lab:<sha>` и останавливается на шаге «production».
3. Руководитель в GitHub открывает **Actions → Deploy → Review deployments → Approve**.
4. GitHub по SSH заходит на сервер под пользователем `deploy`, обновляет `IMAGE` в `.env`, перезапускает контейнеры и проверяет `/health`.

Однократная настройка в GitHub (выполняет владелец репозитория):

| Где | Что |
|---|---|
| Settings → Environments → New: `production` | Required reviewers: руководители |
| Settings → Secrets → Actions | `SSH_HOST`, `SSH_PORT`, `SSH_USER` (=deploy), `SSH_KEY`, `GHCR_READ_TOKEN` |
| Сервер, `~deploy/.ssh/authorized_keys` | открытая часть `SSH_KEY` |

Откат на предыдущую версию:

```bash
cd /opt/energy-lab
sed -i 's#^IMAGE=.*#IMAGE=ghcr.io/<владелец>/energy-lab:<предыдущий sha>#' .env
docker compose -f docker-compose.prod.yml up -d
```

Миграции вниз не откатываются автоматически. Если новая версия меняла схему, перед откатом восстановите копию БД (п. 5.4).

## 7. Аварийные ситуации

| Признак | Причина | Действия |
|---|---|---|
| `/health` не отвечает, сайт 502 | упал `web` | `docker compose -f docker-compose.prod.yml logs --tail=100 web`; частые причины — ошибка в `.env`, недоступна БД. `docker compose … up -d` |
| `web` перезапускается в цикле, в логе `alembic` | миграция не прошла | откатить `IMAGE` на прошлый тег (раздел 6), сообщить разработчику лог |
| nginx не стартует | не заменён `N8N_SERVER_IP` или нет сертификата | исправить `deploy/nginx.conf`, проверить `/etc/letsencrypt/live/<домен>` |
| Бот не отвечает, уведомления не приходят | n8n выключен, неверный `BOT_API_TOKEN`, сменился IP n8n | в n8n посмотреть Executions; `curl -H "Authorization: Bearer …" https://<домен>/api/bot/events` с сервера n8n — 200; при 403 обновить IP в nginx |
| Telegram работает медленно | замедление Telegram в РФ с 10.02.2026 | попросить участников переключить уведомления на ВКонтакте |
| Все пользователи «вылетели» из кабинета | сменился `SECRET_KEY` | это ожидаемо, войти заново; приглашения тоже станут недействительны |
| Руководитель забыл пароль, других руководителей нет | — | `docker compose … exec web python -c "from app.db import SessionLocal; from app import models as m; from app.security import hash_password; s=SessionLocal(); u=s.query(m.User).filter_by(email='…').one(); u.password_hash=hash_password('новый-пароль'); s.commit()"` |
| Нет места на диске | старые образы и копии | `docker image prune -af`; проверить `backups/` |
| Утечка `BOT_API_TOKEN` | — | сгенерировать новый, заменить в `.env` и в credential n8n, `docker compose … up -d` |
| Удаление ПДн по запросу | ст. 21 152-ФЗ | `UPDATE users SET full_name='Удалённый пользователь', email='deleted-'||id||'@invalid', phone=NULL, telegram_id=NULL, vk_id=NULL, is_active=false WHERE id=…;` |

## 8. Рекомендации по освоению

1. Разверните Систему локально: `make dev`. Откройте `http://localhost:8000` и войдите под `oleg@energy.local` / `demo12345`.
2. Пройдите сценарий из Руководства пользователя от лица участника, эксперта и руководителя.
3. Выполните пробное восстановление резервной копии на тестовой машине.
4. Прочитайте `docs/chtz/M08-bot-api.md` перед настройкой n8n.

## Приложение А. Переменные окружения

| Переменная | Обязательна | Описание |
|---|---|---|
| `SECRET_KEY` | да | ключ подписи сессий и приглашений, ≥ 48 случайных символов |
| `BOT_API_TOKEN` | да | токен API для n8n; такой же — в credential n8n |
| `BASE_URL` | да | публичный адрес, например `https://lab.example.ru` (ссылки в уведомлениях) |
| `DATABASE_URL` | да | `postgresql+psycopg://energy_lab:<пароль>@db:5432/energy_lab` |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | да | параметры контейнера PostgreSQL |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | да | первый руководитель (создаётся один раз) |
| `SECURE_COOKIES` | да | `1` на сервере с HTTPS |
| `IMAGE` | да | образ приложения; обновляется CI/CD |
| `BACKUP_GPG_RECIPIENT` | для копий | получатель GPG-ключа резервных копий |

## Приложение Б. Регламент обслуживания

| Периодичность | Действие |
|---|---|
| ежедневно, автоматически | резервная копия, обезличивание старых покупателей, чистка очереди |
| еженедельно | просмотреть «Доска и SOS», журнал Executions в n8n |
| перед каждым сезоном | проверить список экипажа, отключить ушедших, проверить веса критериев |
| ежеквартально | пробное восстановление копии, `apt upgrade` и перезагрузка сервера, проверка срока сертификата |
| после каждого мероприятия | внести факт и завершить «Разбор полёта», чтобы прогноз учился |
