# ЧТЗ М-07. Билеты Timepad и фактические результаты

**Основание:** ТЗ, ЧТЗ-2 (LAB-04 – LAB-06), ЧТЗ-4 (CAB-08).
**Код:** `app/routers/cabinet.py → tickets_import, project_result`, `app/templates/public/event.html` (виджет).

## 1. Назначение

Продавать билеты, не принимая платежей на своём сервере, и получить данные о продажах для факта и прогноза.

## 2. Почему Timepad

Timepad сам принимает оплату, выдаёт чек по 54-ФЗ, рассылает билеты и проводит возвраты. Система хранит только ссылку на событие Timepad и обезличенную выгрузку заказов.

## 3. Функциональные требования

| ID | Требование | Этап |
|---|---|---|
| М07-01 | В проекте поля «ID события Timepad» и «Ссылка на Timepad»; на карточке `/e/{код}` подключается виджет | 1 |
| М07-02 | Если виджет не загрузился за 5 секунд — показывается прямая ссылка | 1 |
| М07-03 | Импорт CSV-выгрузки заказов Timepad: колонки ищутся по названию («Номер заказа», «E-mail», «Сумма», «Статус»), разделитель `;` или `,`, кодировка UTF-8 или Windows-1251 | 1 |
| М07-04 | Повторная загрузка того же файла не создаёт дублей: ключ заказа `{ID события}:{номер заказа}` | 1 |
| М07-05 | Заказ со статусом «Возврат»/«Отменён» помечается `refunded` и не входит в продажи; повторная загрузка обновляет статус | 1 |
| М07-06 | После импорта — число билетов и выручка подставляются в форму факта | 1 |
| М07-07 | E-mail покупателя хранится для сверки анкет «подтверждённый гость» и обезличивается через 30 дней после мероприятия (`python -m app.maintenance`, запускается из `deploy/backup.sh`) | 1 |
| М07-08 | Автоматическая загрузка заказов через API Timepad по вебхуку `order_change` (через n8n) | 2 |

## 4. Данные

`tickets` (`external_order_id` уникален), `event_results`.

## 5. Приёмка

Загрузить один CSV дважды → в базе 2 билета, а не 4 (`test_full_flow`, шаг 5).

## 6. Что нужно от заказчика

Аккаунт организатора Timepad, ID организации, пример настоящей выгрузки заказов (для сверки названий колонок).
