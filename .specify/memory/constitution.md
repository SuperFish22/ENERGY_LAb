# Конституция ИС «Energy Lab»

Информационная система для проведения экспертно-оценочных тренингов педагогического отряда ENERGY (ВКР, НИУ «МЭИ»). Документ задаёт правила, которым подчиняется каждая спецификация, план и задача, созданные через Spec Kit. Основания: ТЗ (общее), ЧТЗ-1…ЧТЗ-5, `docs/chtz/M01…M10`.

## Основные принципы

### I. Персональные данные остаются в России (НЕ ОБСУЖДАЕТСЯ)

- Персональные данные участников, экспертов и покупателей (ФИО, телефоны, e-mail, Telegram ID, заявки) хранятся и обрабатываются только на сервере сайта в РФ — 152-ФЗ.
- n8n и Telegram-бот работают на **внешнем** сервере и получают от сайта только то, что нужно для ответа, через `/api/bot/*` с токеном и белым списком IP.
- Новая интеграция не может хранить ПДн у себя. Если без этого нельзя — фича возвращается на `/speckit-clarify`.
- E-mail покупателей удаляются через 30 дней (`app/maintenance.py`). Новые поля с ПДн получают срок хранения в спецификации.

### II. Секреты — только в окружении (НЕ ОБСУЖДАЕТСЯ)

- `SECRET_KEY`, `BOT_API_TOKEN`, ключи SSH, токены ботов и API живут только в `.env` на сервере и в GitHub Secrets.
- В репозитории, спецификациях, планах, логах и тестах — только `.env.example` с пустыми значениями.
- Утечка секрета означает немедленную ротацию. Удалить строку из истории недостаточно.

### III. Методика экспертизы — проверяемая математика

- Методы А, Б, В, Г, пересчёт компетентности и метрики разбора (MAPE, NPS) живут в `app/expertise/` как чистые функции без обращений к HTTP.
- Числовые параметры методов задаются только в `METHOD` (`app/config.py`). Константы, разбросанные по коду, не допускаются.
- Покрытие `app/expertise` тестами — не ниже 90 % (`--cov-fail-under=90` в CI). Изменение формулы сопровождается тестом с ручным расчётом из ВКР.

### IV. Схема БД меняется только миграциями

- Любое изменение моделей — новая ревизия Alembic (`migrations/versions/00NN_*.py`) с рабочим `downgrade`.
- Миграция проверяется и на SQLite (локально и в тестах), и на PostgreSQL 16 (сервер).
- `create_all` в продакшене не используется, ручные правки схемы на сервере запрещены.

### V. Мероприятие должно быть планируемым

- Главная ценность системы — путь «план → прогноз → факт». Фича, затрагивающая мероприятие, указывает, на какой стадии жизненного цикла (`EVENT_STATUSES`, `TRANSITIONS`) она работает и что меняет в прогнозе или итоговой оценке.
- Переходы статусов идут только по таблице `TRANSITIONS`, недопустимый переход отвечает 403. Каждая смена статуса пишется в `audit_log`.

### VI. Безопасный и понятный интерфейс на русском

- Весь интерфейс, сообщения об ошибках и уведомления — на русском, языком пользователя, а не системы.
- Каждая форма, меняющая данные, защищена CSRF. Права проверяются на сервере по ролям (участник, эксперт, руководитель, администратор), скрытая кнопка защитой не считается.
- Загружаемые файлы проходят проверку сигнатуры и размера (`app/media.py`). Пользовательский ввод не попадает в HTML без экранирования Jinja2.
- Публичная главная страница существует для покупателей: всё на ней настраивается из `/cabinet/admin/site` без правки кода.

### VII. Документация движется вместе с кодом

- Фича закрыта, когда обновлены её ЧТЗ (`docs/chtz/M*.md`: требование с ID, интерфейс, сценарий приёмки со ссылкой на тест) и руководства по ГОСТ 34 (`docs/guides/user.md`, `admin.md`).
- Новые требования получают ID в формате модуля (`М03-12`) и ссылаются на ТЗ.
- Изменения n8n-сценариев делаются в `n8n/generate.py`. JSON в `n8n/workflows/` только генерируется.

## Стек и ограничения

- Python 3.12, FastAPI, Jinja2, SQLAlchemy 2, Alembic. Локально SQLite, на сервере PostgreSQL 16 в Docker (`docker-compose.server.yml`, проект `energylab`, порт `127.0.0.1:8001`).
- Внешние зависимости добавляются только с обоснованием в `plan.md`. SPA-фреймворки на фронте не используются: серверный рендер и небольшой JS.
- Сайт не должен мешать второму проекту на том же сервере (`energy`, порт 8000). Свои порты, свой compose-проект, свой конфиг nginx.
- На продакшен-сервер Claude не ходит. Команды для сервера готовятся как инструкция, выполняет их владелец.
- Пентест (Strix) проводится только на локальной копии, не на продакшене.

## Порядок работы над фичей

1. `/speckit-specify` — что и зачем, без технологий; роли и стадия жизненного цикла мероприятия.
2. `/speckit-clarify` — обязательно, если затронуты ПДн, роли или деньги.
3. `/speckit-plan` — с разделом «Ворота плана» (см. ниже).
4. `/speckit-tasks`, затем `/speckit-analyze`.
5. `/speckit-implement`. Перед коммитом: `ruff check app tests` и `pytest -q --cov=app/expertise --cov-fail-under=90` — зелёные.
6. Баги идут через `/speckit-bug-assess` → `/speckit-bug-test` → `/speckit-bug-fix`: сначала падающий тест.
7. Идеи «а не сделать ли…» сначала проходят `/speckit-assess-*`.

### Ворота плана (Constitution Check)

- [ ] ПДн не уходят за пределы сервера в РФ; для новых полей указан срок хранения (I)
- [ ] Новых секретов в коде нет, есть строки в `.env.example` (II)
- [ ] Параметры методики — в `METHOD`, тесты на формулы есть (III)
- [ ] Изменения схемы — миграцией Alembic с `downgrade` (IV)
- [ ] Указана стадия жизненного цикла и влияние на прогноз и факт (V)
- [ ] Роли, CSRF, русские тексты, проверка загрузок (VI)
- [ ] Перечислены обновляемые ЧТЗ и разделы руководств (VII)

## Управление

- Конституция главнее остальных договорённостей по проекту. При противоречии со спецификацией правится спецификация.
- Поправки вносятся через `/speckit-constitution` с отчётом о влиянии и сменой версии: MAJOR — принцип убран или переопределён, MINOR — добавлен принцип или раздел, PATCH — уточнение формулировок.
- Каждый `plan.md` проходит «Ворота плана». Отступление записывается в таблицу Complexity Tracking с причиной.
